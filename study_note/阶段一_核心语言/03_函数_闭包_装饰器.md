## 0. 先跑起来

```python
# 03_decorator_demo.py
import functools
import time

# ── 1. 函数是一等公民：可以赋值、传参、返回 ──
def add(a, b): return a + b
f = add                      # 函数赋值给变量
print(f(1, 2))               # 3
print(add.__name__)          # 'add'

def apply(fn, x):            # 函数当参数
    return fn(x, x)
print(apply(add, 10))        # 20

# ── 2. 闭包：内部函数"记住"外部函数的变量 ──
def make_scale(factor):      # 外部函数
    def scale(x):            # 内部函数（闭包）
        return x * factor    # 引用了外部的 factor
    return scale             # 返回内部函数

double = make_scale(2)
triple = make_scale(3)
print(double(5), triple(5))  # 10 15  ← 各自记住自己的 factor

# ── 3. 装饰器：函数接收函数、返回函数 ──
def timed(fn):               # 装饰器 = 接收函数，返回"套了壳"的函数
    @functools.wraps(fn)     # 保留原函数的 __name__/__doc__ 等元数据
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = fn(*args, **kwargs)
        print(f"{fn.__name__} 耗时 {time.perf_counter() - t0:.6f}s")
        return result
    return wrapper

@timed                       # 语法糖，等价于 slow = timed(slow)
def slow(n):
    return sum(i * i for i in range(n))

print(slow(10**6))
print("函数名被保留:", slow.__name__)   # 'slow'（若不用 wraps 会变成 'wrapper'）

# ── 4. 带参数的装饰器：三层嵌套 ──
def retry(times=3):          # 第一层：接收"装饰器参数"
    def decorator(fn):       # 第二层：接收"被装饰函数"
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):   # 第三层：真正执行
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    print(f"第 {attempt + 1} 次失败: {e}")
            raise RuntimeError(f"重试 {times} 次仍失败")
        return wrapper
    return decorator

import random
@retry(times=3)              # 等价于 flaky = retry(times=3)(flaky)
def flaky():
    if random.random() < 0.5:
        raise ValueError("随机失败")
    return "成功"

print(flaky())
```

运行：`python 03_decorator_demo.py`。

**先观察**：`double(5)` 和 `triple(5)` 为什么能各自"记住"自己的 `factor`？`@timed` 这一行到底发生了什么？带着这两个疑问读下去。

## 1. 一句话直觉

> **函数是"可以打包带走的一段代码"，闭包是"这段代码带走时，顺手揣进兜里的出生地变量"，装饰器是"给函数套一件外套，让它原来的本事不变，但多了一些新动作"。**

类比：装饰器像**外卖的包装袋**。你点了一份饭（原函数），商家套个袋子（wrapper），袋子上印了广告/贴了单据（额外逻辑），但你吃到的还是那份饭（原函数的行为不变，返回值不变）。`functools.wraps` 则保证"袋子上的名字还是这道菜的名字"。

## 2. 核心原理

### 2.1 函数是一等公民（first-class function）

"一等公民"意味着函数和整数、字符串一样，可以：

| 能力 | 示例 |
|------|------|
| 赋值给变量 | `f = add` |
| 放进容器 | `ops = [add, mul, sub]` |
| 作为参数 | `apply(add, 10)` |
| 作为返回值 | `return scale` |
| 在运行时动态创建 | `lambda x: x + 1` |

> 你在 `model.py` 里已经无意识地用了它：`encode = lambda s: [stoi[c] for c in s]`。lambda 就是"没有名字的一等函数"。

**为什么重要**：AI Infra 里到处都是"把函数当配置传来传去"——回调、钩子（hook）、算子注册、自定义 autograd function 的 `forward`/`backward`。不懂一等函数，就看不懂这些框架的 API。

### 2.2 闭包（closure）：函数 + 它捕获的自由变量

```python
def make_scale(factor):
    def scale(x):
        return x * factor    # factor 不是 scale 的局部变量，也不是全局变量
    return scale
```

`scale` 里用到的 `factor` 既不在自己内部、也不是全局，而是来自**外层函数 `make_scale` 的作用域**。Python 会让 `scale` 这个函数对象"携带"一份对 `factor` 的引用，这个"函数 + 捕获的变量"的整体，就叫**闭包**。

查看闭包捕获了什么：

```python
double = make_scale(2)
print(double.__closure__)             # (<cell ...>,)  ← 有一个被捕获的 cell
print(double.__closure__[0].cell_contents)   # 2  ← 捕获的 factor 值
```

**闭包 vs 默认参数**：闭包捕获的是**变量本身（cell 引用）**，不是"当时的值"。这引出一个经典陷阱：

```python
funcs = []
for i in range(3):
    funcs.append(lambda: i)     # 三个 lambda 都捕获了同一个变量 i
print([f() for f in funcs])     # [2, 2, 2]  ← 不是 [0, 1, 2]！
```

循环结束后 `i` 已经是 2，三个闭包读的是**同一个 `i`**。解法：用默认参数"冻结"值：

```python
funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])     # [0, 1, 2]  ← 正确
```

**修改闭包变量要用 `nonlocal`**：

```python
def counter():
    n = 0
    def inc():
        nonlocal n      # 声明"我要改的是外层那个 n"
        n += 1
        return n
    return inc
c = counter()
print(c(), c(), c())    # 1 2 3
```

### 2.3 装饰器：语法糖 + 高阶函数的组合

装饰器本质就是"**接收函数，返回新函数**"的高阶函数：

```python
@timed
def slow(n): ...
# ↓ 完全等价于 ↓
slow = timed(slow)
```

执行顺序：**定义时**（不是调用时）就完成"套壳"。所以 `@timed` 下面的 `slow` 从这一刻起，已经不是原来的 `slow`，而是 `wrapper`。

**`functools.wraps` 为什么必须加**：不加的话，`slow.__name__` 会变成 `'wrapper'`，`__doc__` 也会丢。这对调试、文档、以及某些框架（它们靠 `__name__` 识别函数）是灾难。**记住：写装饰器必加 `@functools.wraps(fn)`**。

### 2.4 三层嵌套：带参数的装饰器

```python
@retry(times=3)
def flaky(): ...
# ↓ 等价于 ↓
flaky = retry(times=3)(flaky)
```

拆解：`retry(times=3)` 先执行，返回一个真正的装饰器 `decorator`；再 `decorator(flaky)` 返回 `wrapper`。所以"带参数的装饰器"就是**一个"返回装饰器"的函数**，共三层。

**记忆法**：

```
无参装饰器：      decorator(fn) -> wrapper              （2 层）
带参装饰器：      factory(param) -> decorator(fn) -> wrapper  （3 层）
```

### 2.5 类装饰器 & 装饰器类

装饰器不一定要用函数，还可以用**类**（实现 `__call__`）：

```python
class CountCalls:
    def __init__(self, fn):
        functools.update_wrapper(self, fn)
        self.fn = fn
        self.calls = 0
    def __call__(self, *args, **kwargs):
        self.calls += 1
        return self.fn(*args, **kwargs)

@CountCalls
def greet(name): return f"hi {name}"

greet("a"); greet("b")
print(greet.calls)   # 2  ← 带状态的装饰器，比函数版更清晰
```

**装饰器类 vs 装饰器函数**：需要维护跨调用的**状态**（如调用计数、缓存、指标收集）时，类版更清晰。

## 3. 深入细节：装饰器的工业用途全景

装饰器是 Python 工业代码的"瑞士军刀"，你已经在项目里接触到好几类：

| 类别 | 你项目里的实例 | 机制 |
|------|---------------|------|
| **行为开关** | `@torch.no_grad()` | 进入时关梯度、退出时恢复（本质是上下文管理器装饰器） |
| **抽象方法标记** | `@abstractmethod`（backend.py） | 给类打个"此方法必须被子类实现"的标记，配合 `ABC` 元类强制 |
| **类加工** | `@dataclass`（model.py 的 Config） | 不是包函数，而是"加工类"：自动生成 `__init__`/`__repr__`/`__eq__` |
| **属性协议** | `@property` / `@classmethod` / `@staticmethod` | 走描述符协议（第 04 篇） |
| **注册表** | `TORCH_LIBRARY` 内部、你的算子 schema | 把函数登记进一个全局表，供 dispatcher 查找 |
| **性能/观测** | 自写 `@timed` | 横切逻辑（计时、日志、缓存、重试、限流）与业务解耦 |

**最该掌握的四个"自制"装饰器**（面试高频）：

```python
# 1) 计时
def timed(fn):
    @functools.wraps(fn)
    def wrapper(*a, **k):
        t = time.perf_counter(); r = fn(*a, **k)
        print(f"{fn.__name__}: {time.perf_counter()-t:.4f}s"); return r
    return wrapper

# 2) 缓存（纯函数结果缓存，避免重复计算）
from functools import lru_cache
@lru_cache(maxsize=128)
def rope_freqs(head_dim: int, max_len: int) -> tuple:
    return compute_rope_freqs(head_dim, max_len)   # 昂贵计算只算一次

# 3) 重试（网络/加载模型等不稳定的调用）
def retry(times=3, delay=0):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **k):
            for i in range(times):
                try: return fn(*a, **k)
                except Exception as e:
                    if i == times - 1: raise
                    time.sleep(delay)
        return wrapper
    return deco

# 4) 注册表（把算子登记进 dict，dispatcher 按名字查）
REGISTRY = {}
def register(name):
    def deco(fn):
        REGISTRY[name] = fn
        return fn
    return deco

@register("rmsnorm")
def rmsnorm(x, w, eps): ...
```

> 你 `bindings.cpp` 里的 `TORCH_LIBRARY(kernels, m) { m.def(...) }` 就是 C++ 侧的"注册表模式"，和 Python 的 `@register` 装饰器**是同一个思想**：**把"实现"和"按名字分发"解耦**。

## 5. 自测题

**Q1（概念）**：`@dataclass` 和 `@timed` 这两个装饰器，作用对象有什么本质不同？分别"加工"了什么？

**Q2（应用）**：下面代码的输出是什么？为什么？

```python
def make_adder(n):
    return lambda x: x + n

adders = [make_adder(i) for i in range(3)]
print([a(10) for a in adders])
```

**Q3（思考）**：为什么 `@functools.wraps(fn)` 对"被装饰的函数"在 `torch.compile`、`pytest` 这类框架下特别重要？提示：这些框架会读取函数的什么元信息？

<details>
<summary>点击展开答案</summary>

**A1**：`@timed` 作用对象是**函数**，返回一个新的包装函数（在运行时套壳）；`@dataclass` 作用对象是**类**，在类定义时"加工"这个类——根据类注解自动生成 `__init__`/`__repr__`/`__eq__` 等方法。一个包函数，一个改类。同理 `@abstractmethod` 是给"方法对象"加属性标记，`@property` 是走描述符协议把方法变成属性。

**A2**：输出 `[10, 11, 12]`。因为 `make_adder(i)` 每次调用都创建了一个**新的作用域**，`lambda x: x + n` 捕获的是**当次调用**的 `n`（各是 0、1、2）。对比第 2.2 节的陷阱：那个陷阱是"一个循环里多个 lambda 共享同一个循环变量 i"，而这里是"每次函数调用各自独立的局部变量 n"——作用域隔离了。

**A3**：因为这些框架依赖函数的 `__name__`、`__qualname__`、`__doc__`、`__module__` 等元数据。例如 `torch.compile` 需要按 `__qualname__` 定位源码、`pytest` 用 `__name__` 显示测试名和收集用例、`functools.lru_cache` 内部也要读 `__name__`。不加 `wraps`，函数元数据变成 `wrapper`，会导致测试名错乱、`torch.compile` 找不到源函数、日志/调试信息全错。`functools.wraps` 就是把这些元数据从原函数"复制"到包装函数上。
</details>
