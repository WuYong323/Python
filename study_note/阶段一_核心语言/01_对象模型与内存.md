## 0. 先跑起来

把下面代码复制进一个 `.py` 文件跑一遍，先看现象，再看原理：

```python
# 01_object_model_demo.py
import sys
import copy

# ── 1. 变量是"标签"，不是"盒子" ──
a = [1, 2, 3]
b = a                    # b 不是复制了一份，而是给同一个列表又贴了个标签
b.append(4)
print("a =", a)          # [1, 2, 3, 4]  ← a 也被改了！
print("a is b:", a is b) # True，同一对象

# ── 2. 不可变对象"看起来像复制"，其实是换了标签 ──
x = 1000
y = x
print("x is y:", x is y) # True（同一个 int 对象）
y = y + 1                # int 不可变，+ 产生新对象，y 指向新的
print("x =", x, " y =", y)   # 1000  1001
print("x is y:", x is y)     # False

# ── 3. 小整数驻留（interning）陷阱 ──
print("小整数:", 5 is 5)              # True（-5~256 被缓存，永远是同一对象）
print("大整数:", 1000 is 1000)        # True（同一行字面量会被编译器优化复用）
print("大整数跨变量:", x is 1000)      # True（常量池）

# ── 4. 深浅拷贝 ──
nested = [[1, 2], [3, 4]]
shallow = copy.copy(nested)      # 浅拷贝：只复制外层列表，内层还是同一个
deep    = copy.deepcopy(nested)  # 深拷贝：递归复制所有层
shallow[0].append(99)
print("shallow 后 nested =", nested)   # [[1, 2, 99], [3, 4]] ← 内层被共享，污染了
print("deep 是否独立:", deep[0] is nested[0])  # False

# ── 5. 引用计数 ──
o = object()
print("引用计数:", sys.getrefcount(o) - 1)  # -1 是去掉 getrefcount 自己的临时引用
```

运行命令：`python 01_object_model_demo.py`（无需任何第三方依赖）。

**先观察这 5 组输出的"反直觉"处**：为什么 `b.append` 会让 `a` 也变？为什么 `1000 is 1000` 是 True 而 `x is 1000` 也是 True？带着这两个疑问读下去。

## 1. 一句话直觉

> **Python 变量不是"装着值的盒子"，而是"贴在对象上的便利贴"。**

- 别的语言（C/Java）里 `int a = 5` 是"分配一个盒子叫 a，往里放 5"。
- Python 里 `a = 5` 是"造一个值为 5 的整数对象，然后把便利贴 a 贴上去"。
- 一张便利贴能撕下来贴到别的对象上；**多个便利贴可以贴到同一个对象上**；对象上没有便利贴了，就被清理工（GC）收走。

这条直觉能统一解释后面所有现象，包括"为什么显存不释放"——**只要还有一张便利贴贴在张量上，它占的显存就不会还回去**。

## 2. 核心原理

### 2.1 一切皆对象

在 Python 里，整数、字符串、列表、函数、类、模块……**全都是对象**。每个对象有三样东西：

| 属性 | 说明 | 查看方式 |
|------|------|---------|
| **类型** type | 决定它能做什么操作 | `type(obj)` |
| **值** value | 有些对象的值可变，有些不可变 | — |
| **身份** identity | 对象在内存中的唯一编号 | `id(obj)` |

```python
def f(): pass
print(type(1))      # <class 'int'>
print(type(f))      # <class 'function'>  ← 函数也是对象！
print(id(f))        # 一串内存地址编号，运行期唯一
```

> **推论**：既然函数是对象，那么"把函数当参数传、当返回值返回"就是顺理成章的（这是第 03 篇装饰器/回调的基础）。

### 2.2 可变性（mutable）与不可变性（immutable）

| 类别 | 类型 | 含义 |
|------|------|------|
| 不可变 | `int` `float` `str` `tuple` `frozenset` `bytes` | 对象一旦创建，值永远不变；任何"修改"都产生**新对象** |
| 可变 | `list` `dict` `set` `bytearray`、自定义类实例 | 对象内部状态可以原地改变 |

关键区别：**不可变对象的"修改"是假象**——

```python
s = "hello"
s2 = s.upper()      # 不是把 s 改了，而是造了个新字符串 "HELLO"
print(s)            # "hello"  ← s 没变！
```

这就是为什么 `y = y + 1` 之后 `y is x` 变成 False：`+1` 造了个新 `int`，便利贴 `y` 被撕下来贴到新对象上。

**为什么这么设计？** 不可变对象天然线程安全（不会被并发写坏）、可哈希（能当 dict 的 key）、可安全共享（无需防御性拷贝）。这是 Python 大量内部优化（驻留、缓存）的前提。

### 2.3 `is` vs `==`

| 运算符 | 比较的是 | 含义 |
|--------|---------|------|
| `==` | **值** | 两个对象的值相等吗（调用 `__eq__`） |
| `is` | **身份** | 两个引用指向**同一个对象**吗 |

**工业铁律**：
- 和**单例**比较用 `is`：`if x is None`、`if obj is not None`（不要用 `== None`，因为某些对象重载了 `__eq__`，可能对 None 返回意外结果）。
- 其余场景**一律用 `==`** 比较值。

```python
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b)   # True  ← 值相等
print(a is b)   # False ← 两个不同的列表对象
```

### 2.4 驻留（interning）——`is` 时灵时不灵的真凶

Python 为了性能，会**缓存并复用**一些对象，导致 `is` 出现"意外 True"：

```python
a = 256; b = 256;  print(a is b)   # True  ← -5~256 小整数被全局缓存
a = 257; b = 257;  print(a is b)   # 可能是 False！（超出缓存范围，各自新建）
```

还有字符串驻留、编译期常量折叠（同一行写 `1000 is 1000` 编译器会合并成同一对象）。

> **教训**：**永远不要用 `is` 来比较数值/字符串的值**。`is` 只用于 `None`、单例、以及你**故意**要判断"是否同一对象"的场合。这条能避免大量隐蔽 bug。

### 2.5 深浅拷贝

```python
import copy
shallow = copy.copy(obj)      # 浅拷贝：新造一个"外层"容器，但内层元素还是引用原来的
deep    = copy.deepcopy(obj)  # 深拷贝：递归复制每一层，完全独立
```

直观记忆：

```
原始  nested ──→ [ ● , ● ]      （● 是内层列表）
浅拷贝 shallow ──→ [ ● , ● ]    ← 外层是新列表，但内层 ● 还是同一个对象
深拷贝 deep ──→ [ ○ , ○ ]       ← 内外层全是新对象
```

浅拷贝坑在"只复制了一层"：改内层会污染原对象（见第 0 节示例 4）。

**工业应用**：在推理引擎里，如果你要复制一份 KV cache 的 `block_table`（列表的列表）去给某个请求做"快照回滚"，**必须用 `deepcopy`**，否则回滚时改的是同一个物理块引用，会污染别的请求。

## 3. 深入细节：引用计数与垃圾回收（GC）

### 3.1 引用计数：主机制

Python 每个对象内部有个计数器，记录"当前有多少引用指向我"：

- 贴上一张便利贴（赋值、传参、放进容器）→ 计数 +1
- 撕掉一张便利贴（重新赋值、`del`、离开作用域）→ 计数 -1
- **计数归 0 → 立即回收**（确定性、即时）

```python
import sys
def refcount_demo():
    a = [1, 2, 3]
    b = a                    # +1
    print(sys.getrefcount(a) - 1)  # 2（a 和 b 各一个引用）
    del b                    # -1
    print(sys.getrefcount(a) - 1)  # 1
```

### 3.2 分代 GC：解决循环引用

引用计数有个致命盲区——**循环引用**：

```python
class Node:
    def __init__(self):
        self.next = None

a = Node()
b = Node()
a.next = b
b.next = a          # a → b → a，互相引用，计数永远 ≥ 1
del a
del b               # 计数不为 0，引用计数机制永远回收不了它们！
```

所以 Python 加了**分代 GC**：专门扫描容器对象（list/dict/类实例等），找出"只被彼此引用、外界够不着"的循环引用垃圾，周期性回收。

```
分代思想（类比）：
- 第 0 代 = 新生儿（新对象），回收最频繁
- 第 1 代 = 活过一轮的
- 第 2 代 = 长寿对象，回收最不频繁
新生对象大多"早夭"，所以高频扫第 0 代最划算。
```

```python
import gc
gc.collect()          # 手动触发一次全量 GC
gc.get_threshold()    # 查看三代阈值，如 (700, 10, 10)
```

### 3.3 ⭐ 为什么这对你的推理引擎至关重要（显存释放时机）

CUDA 显存是由**引用计数**决定释放时机的，这是 AI Infra 工程师的必懂细节：

```python
import torch

x = torch.randn(1000, 1000, device="cuda")   # 分配一块显存
y = x                                          # y 也指向同一张量，引用计数 = 2
del x                                          # 计数 -1，但不为 0 → 显存不释放！
# 此时显存还被 y 占着，你以为 del x 就释放了，其实没有
del y                                          # 计数归 0 → 此刻显存才真正归还
torch.cuda.empty_cache()                       # 把已释放但被缓存池持有的显存强制还给驱动
```

**真实生产 bug 场景**：你的引擎在推理循环里不断创建中间张量，如果某个张量被错误地长期持有（比如塞进一个全局 list、被闭包捕获、被 `self.xxx = tensor` 挂到对象上忘了清），显存会一路涨到 OOM——**而 `print` 根本看不出问题**。

> 记忆口诀：**"del 只是撕便利贴，不保证立刻释放；谁还贴着便利贴，谁就占着显存；想要确定性释放，管好所有引用 + 必要时 `empty_cache()`。"**

### 3.4 弱引用 `weakref`：工业级缓存的标配

有时我们希望"**不阻止对象被回收，但对象活着时能访问它**"——这就是弱引用：

```python
import weakref

class HeavyTensor:          # 假设这是个大缓存条目
    def __repr__(self): return "<HeavyTensor>"

cache = weakref.WeakValueDictionary()   # 弱引用字典：值被回收后自动消失

obj = HeavyTensor()
cache["k"] = obj
print("cache 里有:", "k" in cache)      # True

del obj                              # 外界唯一强引用没了 → 对象被回收
print("cache 里有:", "k" in cache)      # False ← 自动消失，不占内存！
```

**为什么重要**：vLLM、Transformers 等推理框架的缓存（如 tokenizer cache、编译 kernel cache）大量用弱引用，**保证"缓存不拖累内存回收"**。你以后写"算子结果缓存"时，选 `WeakValueDictionary` 而不是普通 `dict`，就能避免"缓存把显存/内存永远占住"的经典泄漏。

## 4. 回到你的项目

现在对照你的 `推理引擎/engine/PagedAttention.py`，看对象模型如何落地：

1. **`BlockAllocator` 的 `free_blocks` 是共享可变对象**：
   ```python
   self.free_blocks = list(range(num_blocks))   # 一个 list，被所有 Sequence 共享
   ```
   你的 `Sequence` 都持有同一个 `allocator`，所以它们通过 `allocator.free_blocks` **共享同一份物理块池**——这正是"多个便利贴贴同一个对象"在起作用。理解这点，才能理解为什么某个 Sequence 申请块会影响别的 Sequence。

2. **`block_table` 的深拷贝问题**：如果你要支持"请求快照/回滚"，`copy.copy(seq.block_table)` 只复制外层列表，内层物理块编号虽然不可变（int）所以浅拷贝也安全——**但**如果你的 block table 将来存的是可变对象（比如每个块的状态），就必须 `deepcopy`。这是对象模型知识直接决定 API 正确性的地方。

3. **给 `locate` 加防御**：`locate` 里 `self.block_table[logical_block]` 会因越界抛 `IndexError`。理解对象模型后，你会更自然地想到"这里的引用来自哪个对象、谁来保证它存在"，进而补类型和校验（第 07、09 篇会做）。
