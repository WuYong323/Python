# 08 · 类型系统（下）：高级类型与静态检查实战

> **一句话定位**：`Protocol`/`TypedDict`/`Literal`/泛型/PEP 695 这些高级类型，让你能精确描述"接口、数据结构、有限取值、容器"；把 mypy 调到 `--strict`，类型系统就从"提示"升级成"逼出正确性"。
> **前置依赖**：07 类型基础
> **预计时长**：1 天
> **对应你的项目**：`Backend` 是天然的 `Protocol`、`Config` 是天然的 `TypedDict`/dataclass、`causal: bool` 可用 `Literal` 收窄。

## 0. 先跑起来

```python
# 08_typing_advanced_demo.py
from __future__ import annotations
from typing import Protocol, TypedDict, Literal, Annotated, Final, ClassVar, TypeVar

# ── 1. Protocol：结构化子类型（鸭子类型的"静态化"） ──
class SupportsRMSNorm(Protocol):          # 只要"有这个方法"就算符合协议
    def rmsnorm(self, x: object, weight: object, eps: float = ...) -> object: ...

class TorchBackend:                        # 注意：不继承 SupportsRMSNorm！
    def rmsnorm(self, x, weight, eps=1e-6):
        return x

class TritonBackend:                       # 也不继承
    def rmsnorm(self, x, weight, eps=1e-6):
        return x

def use(backend: SupportsRMSNorm) -> None: # 接受"任何有 rmsnorm 的对象"
    backend.rmsnorm(None, None)

use(TorchBackend())    # ✅ 结构化匹配：有 rmsnorm 就算符合，无需继承
use(TritonBackend())

# ── 2. TypedDict：给"字典"精确描述形状 ──
class Request(TypedDict):
    op: str
    hidden: int
    causal: bool

r: Request = {"op": "ffn", "hidden": 172, "causal": True}   # 键和类型都被约束

# ── 3. Literal：限定到"某几个字面值" ──
def set_device(dev: Literal["cpu", "cuda"]) -> None: ...
set_device("cuda")   # ✅
# set_device("gpu")  # ❌ mypy 报错：只能是 "cpu" 或 "cuda"

# ── 4. 泛型 + PEP 695（3.12+ 的 type 语法） ──
def first[T](items: list[T]) -> T:        # 新式泛型：类型参数写在中括号
    return items[0]

print(first([1, 2, 3]))                   # 1，T 被推断为 int
print(first(["a", "b"]))                  # 'a'，T 被推断为 str

class Stack[T]:
    def __init__(self) -> None:
        self._items: list[T] = []
    def push(self, item: T) -> None:
        self._items.append(item)
    def pop(self) -> T:
        return self._items.pop()

s = Stack[int]()                          # 指定 T = int
s.push(1)

# ── 5. 其他常用 ──
MAX_LAYERS: Final = 128                    # Final：不可再赋值
class C:
    shared: ClassVar[int] = 0              # ClassVar：类变量（不是实例属性）
    def __init__(self) -> None:
        self.x: int = 0                    # 实例属性

UserId = Annotated[int, "必须大于 0"]       # Annotated：给类型附加元信息（校验/文档用）
```

运行：`python 08_typing_advanced_demo.py`。然后 `mypy 08_typing_advanced_demo.py` 看它如何抓出 `set_device("gpu")` 之类的错误。

## 1. 一句话直觉

> **`Protocol` 说"我不在乎你是谁家的，只要你提供这个能力"；`TypedDict` 说"这个字典的每个键我都规定了类型"；`Literal` 说"你只能在这几个值里选"；泛型说"我先不指定具体类型，用的时候再定，但前后必须一致"。**

类比：`Protocol` 像招聘启事"招会开叉车的人"——不要求你毕业于哪个学校（不要求继承），只要求你会开叉车（有方法）。`TypedDict` 像**填表格**——每一栏填什么类型都印好了。`Literal` 像**选择题**——A/B/C 之外不能填。泛型像**"能装任意东西、但一个箱子只装一种东西"的收纳箱**。

## 2. 核心原理

### 2.1 `Protocol` vs `ABC`：什么时候用哪个

| | ABC（抽象基类） | Protocol |
|---|----------------|----------|
| 关系 | **名义子类型**：必须显式继承 | **结构化子类型**：有方法就行，无需继承 |
| 适用 | 你要"强制继承 + 提供默认实现/共享状态" | 你要"只描述接口，让第三方/不同体系的类天然兼容" |
| 运行时 | 会强制（无法实例化未实现的子类） | 默认纯标注，不强制 |

**你项目的关键洞察**：`Backend` 用 `ABC` 是对的（因为 `TorchBackend` 是"你的"类，你愿意让它继承）；但如果有一天你想让**外部用户传入"任何实现了 `rmsnorm/attention/fused_ffn` 的对象"**（而不强制继承你的 `Backend`），就该用 `Protocol`。两者可并存：

```python
class Backend(Protocol):          # 结构化协议：只要"长得像后端"即可
    def rmsnorm(self, x: torch.Tensor, weight: torch.Tensor, eps: float = 1e-6) -> torch.Tensor: ...
    ...

def run_model(backend: Backend):  # 接受任何实现了这三方法的对象
    ...
```

> 记忆：**"要共享实现用 ABC，要描述能力用 Protocol"**。这也是 FastAPI、sqlalchemy 等框架大量用 Protocol 的原因——降低耦合。

### 2.2 `TypedDict`：字典的"形状约束"

普通 `dict[str, int]` 只能说"键是 str、值是 int"，说不出"必须有 `op` 这个键、`hidden` 必须是 int"。`TypedDict` 能：

```python
class Request(TypedDict, total=False):   # total=False：所有键可选
    op: str
    hidden: int
```

**用途**：API 请求/响应体、配置字典、JSON 数据。你 `model.py` 里的 `config = {'vocab_size': ..., 'n_embd': ...}` 就是典型的"该用 TypedDict 或 dataclass"的场景（dataclass 更好，见下）。

### 2.3 `Literal`：把"布尔/枚举"收窄到字面量

```python
def norm_kind(kind: Literal["rms", "layer"]) -> None: ...
```

**用途**：替代"魔法字符串"的轻量方案。当你不想要完整 `Enum`（第 04 篇）时，`Literal` 能在静态期就拦住拼写错误。**但注意**：`Literal` 只在静态检查期有效，运行时仍接受任何值；`Enum` 运行时也强制。**"配置/协议字段"用 Literal 合适，"要真正运行期安全 + 携带方法"用 Enum**。

### 2.4 泛型：写一次，处处复用

泛型解决"逻辑相同、类型不同"的重复。两种写法：

```python
# 旧式（typing.TypeVar，3.11 前）：
from typing import TypeVar
T = TypeVar("T")
def first(items: list[T]) -> T: ...

# 新式（PEP 695，3.12+）：
def first[T](items: list[T]) -> T: ...      # 类型参数写在中括号，无需先声明 T
```

**PEP 695 还引入了 `type` 别名语句**：

```python
type Tensor = torch.Tensor            # 3.12+ 新式类型别名
type Batch = tuple[Tensor, Tensor]
```

> 你项目的 `Config`、`Backend`、`Batch` 这些概念，用 PEP 695 的 `type` 别名和泛型，能让代码意图更清晰。**约定：3.12+ 环境统一用 PEP 695 新语法**。

### 2.5 类型窄化（type narrowing）：让检查器"跟着你的 if 走"

```python
def f(x: int | None) -> int:
    if x is None:          # mypy 知道：这个分支里 x 是 None
        return 0
    return x + 1           # mypy 知道：这里 x 一定是 int（已排除 None）
```

`if x is None`、`isinstance(x, int)`、`match` 的 case 绑定，都能让 mypy **自动收窄类型**。这是渐进式类型"既灵活又安全"的关键。

## 3. 深入细节：把 mypy 调到 `--strict`

`--strict` 开启全部严格选项，是"工业级"的验收线。在 `pyproject.toml` 里配置：

```toml
[tool.mypy]
strict = true
python_version = "3.12"
# 忽略第三方库没类型的问题（torch 有 stub，但有些小库没有）
ignore_missing_imports = false
```

**`--strict` 会强制你处理这些**（都是工业代码该做的）：

1. **所有函数都要标注**（禁 `untyped def`）——`disallow_untyped_defs`。
2. **不能有 `Any`**——`disallow_any_generics` 等。
3. **可选值必须显式处理**——`no_implicit_optional`。

**实操命令**：

```powershell
mypy --strict 推理引擎/engine/backend.py
```

**渐进策略**（别一上来被几百个错吓退）：先对**核心模块**开 strict，其他模块逐步覆盖。这也是业界真实做法（先 strict 新代码，老代码渐进）。

**mypy 常见报错与修复**：

| 报错 | 含义 | 修复 |
|------|------|------|
| `Missing return statement` | 有分支没 return | 补 return 或明确返回类型 |
| `Incompatible types in assignment` | 赋值类型不符 | 修正类型或加收窄 |
| `Item "None" has no attribute ...` | 没处理 None | 加 `if x is not None` 收窄 |
| `Function is missing a type annotation` | strict 下没标注 | 补标注 |

**mypy vs pyright vs ty 怎么选**：**mypy** 生态老、规则稳、CI 门禁首选；**pyright**（微软）快、增量检查好，VSCode/PyCharm 用它的引擎做实时提示；**`ty`**（Astral——uv/ruff 团队 2025 年推出的 Rust 类型检查器）很新、极快、生态仍在完善。**建议：IDE 实时提示用 pyright，CI 里跑 mypy 做门禁，`ty` 保持关注、待其成熟**。你机器上 pyright 还没装，用 `uv tool install pyright` 补上。

## 4. 回到你的项目

1. **把 `Backend` 改成 `Protocol`（或并存）**：让上层 `model.py` 只依赖"后端协议"，而不是具体 `TorchBackend`——这直接体现你 `backend.py` 开头注释写的"上层只认接口、不认实现"的意图。
2. **`Config` 用 `TypedDict` 或 dataclass**：`model.py` 里 `config = {'vocab_size': ..., ...}` 裸 dict 改成 `TypedDict`，让每个键的类型被检查（第 18 篇还会升级成 pydantic）。
3. **`causal: bool` 收窄**：如果将来有 `causal: Literal[True]` 或 `mask: Literal["causal", "none", "padding"]` 的区分，用 `Literal` 表达。
4. **对 `backend.py` 开 `--strict`**：把报错清零，这是你阶段二的第一个硬性验收。

## 5. 自测题

**Q1（概念）**：`Protocol` 和 `ABC` 的核心区别是什么？什么时候该选 `Protocol`？

**Q2（应用）**：把下面裸 dict 改成 `TypedDict`，并写出 `process` 的完整类型：

```python
def process(req):
    if req["op"] == "attn":
        return req["hidden"] * 2
    return req["hidden"]
```

**Q3（思考）**：`Literal["cpu", "cuda"]` 和 `Enum`（`class Device(Enum): CPU; CUDA`）都能限制取值，运行时行为有何不同？为什么"需要运行时强制 + 携带方法"时选 Enum？

<details>
<summary>点击展开答案</summary>

**A1**：`ABC` 是**名义子类型**——必须显式继承才成立，且运行时强制（未实现抽象方法无法实例化），适合"你要提供共享实现/共享状态、强制继承"。`Protocol` 是**结构化子类型**——只要有对应方法就算符合、无需继承，默认纯静态（运行时通常不强制），适合"只描述接口、让第三方类天然兼容、解耦"。当你想接受"任何实现了某组方法的对象"而不强制它继承你的基类时，选 `Protocol`。

**A2**：
```python
class Request(TypedDict):
    op: Literal["attn", "ffn"]     # 或 str
    hidden: int

def process(req: Request) -> int:
    if req["op"] == "attn":
        return req["hidden"] * 2
    return req["hidden"]
```

**A3**：`Literal` 只在**静态检查期**由 mypy 把关，**运行时不强制**——你传入 `"gpu"` 程序照跑不误；`Enum` 是**运行时真实的对象**，`Device.GPU` 若不存在会直接 `AttributeError`，且成员是单例、可 `is` 比较、可挂方法和值。因此需要"运行期也拦住非法值 + 携带行为/数据"时选 Enum；只需"静态期提示 + 轻量"时用 Literal。
</details>
