# 09 · 异常与日志：让错误"可定位、可追溯"

> **一句话定位**：异常是"程序遇到预料外情况的通信协议"，日志是"运行时的黑匣子"。工业代码的区别在于——出错时是抛出一个**带上下文**的异常 + 留下**结构化日志**，而不是打印一句 `print` 就裸奔。

> **预计时长**：1 天

## 0. 先跑起来

```python
# 09_exception_logging_demo.py
import logging

# ── 1. 异常层次：自定义异常继承 Exception ──
class InferenceError(Exception):        # 你的引擎所有异常的"根"
    """推理引擎异常的基类。"""

class OutOfMemoryError(InferenceError): # 更具体的异常
    def __init__(self, requested: int, available: int):
        self.requested = requested
        self.available = available
        super().__init__(f"显存不足：需要 {requested} 块，只剩 {available} 块")

# ── 2. try/except/else/finally 全谱 ──
def allocate(blocks_needed: int, free: int) -> None:
    try:
        if blocks_needed > free:
            raise OutOfMemoryError(blocks_needed, free)
        result = 100 // blocks_needed          # 可能 ZeroDivisionError
    except OutOfMemoryError as e:
        print("捕获到自定义异常:", e)          # 具体异常先捕获
    except ZeroDivisionError:
        print("除零了")
    else:
        print("没异常才执行这里:", result)     # else：无异常时执行
    finally:
        print("无论如何都执行（清理资源）")     # finally：一定执行

allocate(2, 5)     # 正常：走 else + finally
allocate(10, 5)    # 触发 OutOfMemoryError
allocate(0, 5)     # 触发 ZeroDivisionError

# ── 3. 异常链：raise ... from ──
def load_model(path: str) -> None:
    try:
        import torch
        torch.load(path, weights_only=True)   # ✅ 加 weights_only，防反序列化攻击
    except FileNotFoundError as e:
        # 用 from 把"底层原因"和"业务异常"串起来，保留完整因果链
        raise InferenceError(f"模型文件不存在: {path}") from e

try:
    load_model("不存在.pt")
except InferenceError as e:
    print("业务异常:", e)
    print("根因:", e.__cause__)                # FileNotFoundError 被保留在 __cause__

# ── 4. logging：结构化、分级、可配置 ──
logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s")
log = logging.getLogger("inference")          # 每个模块用 __name__ 命名 logger

log.debug("调试信息，默认不显示")              # DEBUG < INFO
log.info("开始加载模型")
log.warning("显存使用率达 90%")
log.error("算子执行失败", exc_info=True)       # exc_info=True 附带完整堆栈
```

运行：`python 09_exception_logging_demo.py`。

## 1. 一句话直觉

> **异常 = "向上级打报告"的通信机制；日志 = "黑匣子录音"。异常告诉你"哪一步出错了、为什么"，日志告诉你"一路走来发生了什么"。**

类比：异常像公司里的**逐级上报**——基层（底层函数）出问题，写一份报告（raise 异常）往上抛，直到有能处理的人（except）接手；没人接，就一路抛到顶层崩溃（进程退出）。日志像**行车记录仪**——平时默默记录，出事时回放，就能还原"到底哪一步开始不对劲"。

## 2. 核心原理

### 2.1 异常层次结构

```
BaseException                    ← 所有异常的根（一般不要直接 except 它）
├── SystemExit                   ← sys.exit() 抛的
├── KeyboardInterrupt            ← Ctrl+C 抛的
├── GeneratorExit                ← 生成器关闭
└── Exception                    ← 业务异常的根（你要 catch 的通常是它）
    ├── ValueError
    ├── TypeError
    ├── KeyError
    ├── FileNotFoundError
    ├── MemoryError
    └── ... 你自定义的 InferenceError 等
```

**工业铁律**：
1. **永远不要写裸 `except:`**（会连 `SystemExit`/`KeyboardInterrupt` 都吞掉，用户 Ctrl+C 都停不下来）。
2. **至少 `except Exception:`**，最好**精确到具体异常类型**（`except FileNotFoundError:`）。
3. **自定义异常继承 `Exception`**（不是 `BaseException`），并建立**层次**（根异常 + 具体异常）。

### 2.2 自定义异常：带上"事故现场"

好异常 = 类型（可分类）+ 信息（可读）+ 上下文（可追溯）：

```python
class OutOfMemoryError(InferenceError):
    def __init__(self, requested: int, available: int):
        self.requested = requested          # 把关键数字存成属性
        self.available = available
        super().__init__(f"显存不足：需要 {requested} 块，只剩 {available} 块")
```

> 你 `PagedAttention.py` 的 `raise MemoryError("显存块用尽...")` 是对的思路，但可以升级成带 `requested/available` 字段的自定义异常，这样上层能**按异常类型和字段做决策**（比如触发抢占），而不是只能看字符串。

### 2.3 异常链 `raise ... from`

当你在 `except` 块里又想抛一个新异常时，用 `from` 把原始异常"链"起来：

```python
try:
    torch.load(path)
except FileNotFoundError as e:
    raise InferenceError(f"模型不存在: {path}") from e   # 保留因果链
```

- `from e` → 新异常的 `__cause__` 指向 `e`，堆栈会显示"直接原因是 e"。
- 不用 `from` 也会隐式设置 `__context__`，但显式 `from` 语义更清晰。

**为什么重要**：线上排障时，你最怕看到"中间异常把底层异常吞掉、只剩一句没头没尾的报错"。`from` 保证**根因永远可追溯**。

### 2.4 `assert` vs 显式异常：工业代码少用 assert

```python
assert n_embd % n_head == 0    # ❌ 隐患：python -O 会删掉这行！
```

`assert` 的致命问题：**`python -O`（优化模式）会移除所有 assert**，你的校验就"凭空消失"了。工业代码的校验应该**永远生效**：

```python
if n_embd % n_head != 0:
    raise ValueError(f"n_embd({n_embd}) 必须能被 n_head({n_head}) 整除")
```

> **原则**：`assert` 只用于"开发期自检、绝不该被关掉的内部不变量"；**所有面向输入/配置的校验，用显式 `if + raise`**。你 `model.py` 里的 `assert n_embd % n_head == 0` 应改成 `raise ValueError`（第 04 篇也提过，这里从"生产安全"角度再强调）。

### 2.5 logging：四级 + 按模块命名

```python
import logging
log = logging.getLogger(__name__)   # 每个文件用自己模块名，形成层次
log.info("...")
```

**四级日志的语义**：

| 级别 | 用途 | 生产环境默认开吗 |
|------|------|-----------------|
| DEBUG | 调试细节（张量形状、中间值） | 关 |
| INFO | 关键流程节点（开始加载、训练第 N 步） | 开 |
| WARNING | 非致命异常（显存 90%、精度下降） | 开 |
| ERROR | 出错但程序还能继续 | 开 |
| CRITICAL | 致命，程序要崩 | 开 |

**为什么用 logging 而不是 print**：
1. **分级**：生产环境只开 INFO 以上，DEBUG 不刷屏；print 全都要么全开要么全关。
2. **可配置**：logging 能输出到文件、加时间戳、加模块名、按级别过滤，不用改代码。
3. **可聚合**：`getLogger(__name__)` 形成树状命名空间，可整体控制某个包（如 `inference.*`）的日志级别。
4. **可扩展**：能接 `structlog` 做结构化日志（输出 JSON，方便日志系统采集分析）。

**`exc_info=True`**：`log.error("...", exc_info=True)` 会把完整堆栈打进日志，这是排障的救命稻草。

## 3. 深入细节：结构化日志 structlog（进阶）

`structlog` 让日志变成**结构化键值对**（JSON），便于大规模日志系统（ELK/Loki）检索：

```python
import structlog
log = structlog.get_logger()

log.info("kernel_launched", kernel="vector_add", grid=128, block=256, device="cuda")
# 输出类似：{"event": "kernel_launched", "kernel": "vector_add", "grid": 128, ...}
```

**对比**：普通日志是"人读的句子"，结构化日志是"机器可查的字段"。你以后做推理 serving，需要按 `request_id` 追踪每个请求的完整生命周期，`structlog` 的 `log.bind(request_id=...)` 是标配。

```python
req_log = log.bind(request_id="abc123")   # 绑定额外上下文
req_log.info("token_generated", step=10)  # 每条日志都自动带 request_id
```

## 5. 自测题

**Q1（概念）**：为什么不能写裸 `except:`？它和 `except Exception:` 的区别是什么？

**Q2（应用）**：写出一个"读配置文件 + 校验"的函数，要求：文件不存在抛 `ConfigError` 并保留根因；校验失败抛 `ConfigError` 并带字段名；用 `finally` 保证文件句柄关闭。

**Q3（思考）**：`log.error("...", exc_info=True)` 和 `log.error(f"...{e}")` 有什么区别？为什么前者对排障更重要？

<details>
<summary>点击展开答案</summary>

**A1**：裸 `except:` 会捕获**一切**异常，包括 `SystemExit`、`KeyboardInterrupt`、`GeneratorExit` 这些"控制流"异常——导致用户 Ctrl+C 无法中断、`sys.exit()` 失效、生成器关闭被吞，是灾难性的。`except Exception:` 只捕获业务异常，不拦控制流异常，是能接受的最低标准；更推荐精确到具体异常类型。

**A2**（示例）：
```python
class ConfigError(Exception):
    def __init__(self, msg, field=None):
        self.field = field
        super().__init__(msg)

def load_config(path):
    f = open(path)
    try:
        data = json.load(f)
        if data.get("n_embd", 0) <= 0:
            raise ConfigError("n_embd 必须为正", field="n_embd")
        return data
    except FileNotFoundError as e:
        raise ConfigError(f"配置文件不存在: {path}") from e
    except json.JSONDecodeError as e:
        raise ConfigError("配置不是合法 JSON") from e
    finally:
        f.close()          # 或改用 with open(path) as f
```

**A3**：`log.error(f"...{e}")` 只记录了**异常对象的字符串**，丢了堆栈（不知道异常在哪一行、调用链如何）；`exc_info=True` 记录**完整 traceback**（文件、行号、调用栈），排障时能直接定位到出错代码行。生产排障**必须用 `exc_info=True`**（或 `log.exception(...)`）。
</details>
