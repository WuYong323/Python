## 0. 先跑起来

```python
# 14_memory_demo.py
import sys
import tracemalloc

# ── 1. 测量对象大小：sys.getsizeof ──
print("空 list:", sys.getsizeof([]))           # 56 字节
print("装 1 个元素:", sys.getsizeof([1]))       # 64
print("装 100 万:", sys.getsizeof([0]*1_000_000))  # 8,000,056 字节 ≈ 8MB

# 注意：getsizeof 只算"容器本身"，不算里面元素。要算总内存用 tracemalloc 或递归。

# ── 2. tracemalloc：追踪内存分配，查泄漏 ──
def leaky():
    global _cache
    _cache = [bytearray(1024) for _ in range(1000)]   # 假装泄漏：塞进全局

tracemalloc.start()
snap1 = tracemalloc.take_snapshot()
leaky()
snap2 = tracemalloc.take_snapshot()

top = snap2.compare_to(snap1, "lineno")   # 对比两个快照的差异
for stat in top[:3]:
    print(stat)                            # 显示哪一行分配了多少内存

# ── 3. 省内存：生成器 vs 列表 ──
# 列表：一次性构造 1000 万个 int（约 280MB）
# big_list = [i * i for i in range(10_000_000)]

# 生成器：懒加载，几乎不占内存
big_gen = (i * i for i in range(10_000_000))
print("生成器大小:", sys.getsizeof(big_gen))   # 只有几百字节！

print(sum(big_gen))                          # 用到时才逐个算

# ── 4. __slots__ 省内存 ──
class Normal:
    def __init__(self, x): self.x = x

class Slim:
    __slots__ = ("x",)
    def __init__(self, x): self.x = x

n, s = Normal(1), Slim(1)
print("普通类实例:", sys.getsizeof(n.__dict__))   # 有 __dict__，占内存
print("slots 实例:", sys.getsizeof(s))            # 无 __dict__，更小
# 海量小对象时，__slots__ 差异巨大
```

运行：`python 14_memory_demo.py`。

## 1. 一句话直觉

> **省内存三件套：懒加载（生成器）、轻对象（`__slots__`）、批量算（向量化）。查泄漏靠"前后快照对比"（tracemalloc）。**

类比：内存像**仓库**——列表是"一次把 1000 万件货全搬进仓库"（占满），生成器是"要一件、造一件"（仓库几乎空的）；`__slots__` 是"给货物定做刚好尺寸的货架"（不留多余空间）；向量化是"用叉车一次搬一托盘"（批量操作，比一件件搬快）。

## 2. 核心原理

### 2.1 测量：`sys.getsizeof` 和 `tracemalloc`

```python
sys.getsizeof(obj)   # 对象"自身"占的字节数（浅层，不含引用的元素）
```

**注意陷阱**：`getsizeof([1,2,3])` 只算列表壳，不算里面 int 的内存。要算"总内存"，要么用 `tracemalloc`，要么递归求和。

`tracemalloc` 能**追踪"谁、在哪一行、分配了多少内存"**，核心用法是**快照对比**：

```python
tracemalloc.start()
snap1 = tracemalloc.take_snapshot()
# ... 运行可疑代码 ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:5]:   # 差异排序
    print(stat)
```

**查泄漏的通用套路**：`跑一遍 → 快照 A → 再跑 N 遍 → 快照 B → 对比`，如果某行内存在持续增长，就是泄漏点。

### 2.2 省内存四大手段

| 手段 | 原理 | 省多少 |
|------|------|--------|
| **生成器** | 懒加载，不一次性构造 | 大（几 GB → 几乎 0） |
| **`__slots__`** | 去掉实例的 `__dict__` | 每个对象省几十字节 |
| **向量化** | numpy/torch 批量算，替代 Python 循环 | 快 10~100 倍，且减少中间对象 |
| **`array`/`bytes`** | 用紧凑的 C 数组替代 list[int] | 数倍 |

**生成器**（第 02 篇讲过，这里从内存角度重申）：处理"数据量大但只需逐个消费"的场景（token 流、batch 迭代、逐行读文件），**用生成器而非 list**。

**`__slots__`**：当你有**海量小对象**（如每请求的块元数据、每 token 的状态），省掉 `__dict__` 能显著降内存。**但先测量再决定**（第 2.1 节），别一上来就到处 `__slots__`。

### 2.3 向量化：让 C 层替你循环

```python
# ❌ Python 循环：慢 + 产生大量中间 int
s = 0
for i in range(1_000_000):
    s += i * i

# ✅ 向量化：整个数组一次算完（C 层，释放 GIL，快数十倍）
import numpy as np
x = np.arange(1_000_000)
s = (x * x).sum()
```

**AI Infra 里的向量化 = torch 张量操作**：你能用 `torch.rsqrt`、`torch.mean`、`torch.matmul` 就绝不写 Python 循环逐元素算。你的 `backend.py` 已经这么做了（`x.pow(2).mean(...)` 而非 for 循环）——这是对的。

### 2.4 字符串/列表的常见浪费

```python
# ❌ 字符串 += 拼接：每次产生新字符串，O(n^2)
s = ""
for part in parts:
    s += part

# ✅ join：一次拼接
s = "".join(parts)

# ❌ list 头部插入/删除是 O(n)
# ✅ 用 deque 或"从尾部操作"
```

## 3. 深入细节：torch 显存的精细管理

你的引擎是 GPU 程序，显存管理是**生死线**。核心 API：

```python
import torch

# 当前已分配显存（字节）
print(torch.cuda.memory_allocated())

# 峰值显存（可用来查"谁在峰值时刻占最多"）
print(torch.cuda.max_memory_allocated())

# 把"已释放但被缓存池持有"的显存强制还给驱动
torch.cuda.empty_cache()

# 重置峰值统计（用于分段测量）
torch.cuda.reset_peak_memory_stats()
```

**三个关键认知**（第 01 篇已埋下伏笔，这里收口）：

1. **显存释放由引用计数决定**：只要还有引用指向张量，`del` 也不释放（第 01 篇）。
2. **`empty_cache()` 不是"释放"，是"归还缓存池"**：PyTorch 有个**显存缓存分配器**（caching allocator），张量释放后显存先回池，下次分配直接复用（快）；`empty_cache()` 才把池里的显存还给 CUDA 驱动。**频繁 `empty_cache()` 反而变慢**（下次分配要重新向驱动申请），只在"确认要释放给别的进程/查泄漏"时用。
3. **推理引擎的显存大头是 KV cache**：你的 `PagedAttention` 把 KV cache 分成固定块、按需分配，就是为省显存。第 22 篇会深化到"内存池 + 抢占 + 复用"的生产级设计。

**梯度内存（训练专属）**：`loss.backward()` 会为每个需要梯度的张量保留梯度，`optimizer.zero_grad(set_to_none=True)`（你已经在用）用 `None` 而非 0 清零，能省一点显存。`torch.no_grad()` 推理时关梯度，你也在用。

## 5. 自测题

**Q1（概念）**：`sys.getsizeof([1,2,3])` 为什么不等于三个 int 的总内存？`tracemalloc` 是怎么解决这个问题的？

**Q2（应用）**：把下面的代码改成省内存的版本（不改变结果）：

```python
data = [int(line.strip()) for line in open("big.txt")]
total = sum(x * x for x in data)
print(total)
```

**Q3（思考）**：`torch.cuda.empty_cache()` 为什么"不能随便频繁调用"？它和"张量引用计数归零释放显存"是什么关系？

<details>
<summary>点击展开答案</summary>

**A1**：`getsizeof` 只算**容器对象自身**占的字节（列表的壳 + 指向元素的指针数组），**不算被引用的元素对象**（三个 int 各自的对象）。`tracemalloc` 追踪的是**每次内存分配的来源**（哪一行、分配了多少），它按"分配记录"统计总字节，因此能把元素对象的分配也算进去，从而得到更接近真实的总内存。

**A2**：改成逐行生成器，避免一次性把 `data` 整个 list 载入：
```python
total = sum(int(line.strip()) ** 2 for line in open("big.txt"))
print(total)
```
或至少 `data` 用生成器表达式。核心：**不在内存里保留整个 data list**，边读边算。

**A3**：`empty_cache()` 是把"PyTorch 缓存分配器里已释放、但暂存的显存"强制归还给 CUDA 驱动。它与引用计数释放的关系：张量引用归零 → 显存回到**PyTorch 的缓存池**（并未还给驱动）→ `empty_cache()` 才把池还给驱动。**不能频繁调用**是因为：归还后，下次分配张量要重新向 CUDA 驱动申请（昂贵、慢），失去缓存池"直接复用"的性能优势。所以 `empty_cache()` 只应在"确需把显存让给别的进程/排查泄漏"时用，不应放进热路径。
</details>
