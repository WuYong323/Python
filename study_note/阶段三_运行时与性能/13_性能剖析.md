# 13 · 性能剖析：先测量，再优化

> **一句话定位**：性能优化的第一铁律是"**先测量，再优化**"。`cProfile`/`py-spy`/`line_profiler`/`snakeviz` 帮你找到真正的热点，而不是凭感觉瞎改。
> **前置依赖**：01 对象模型
> **预计时长**：1 天
> **对应你的项目**：你的引擎有 Python 调度层 + torch 计算层，剖析时要分清"Python 慢"还是"GPU 慢"。

## 0. 先跑起来

先装工具：

```powershell
uv tool install py-spy snakeviz line_profiler   # 或用 pip
```

```python
# 13_profile_demo.py
import time

def slow_python(n: int) -> int:
    """纯 Python 慢函数：作为剖析对象"""
    s = 0
    for i in range(n):
        s += i * i
    return s

def fast_builtin(n: int) -> int:
    """用内建 sum + 生成器，快很多"""
    return sum(i * i for i in range(n))

def workload():
    total = 0
    for _ in range(100):
        total += slow_python(10000)      # 热点：这里最耗时
        total += fast_builtin(10000)     # 这里快
    return total

if __name__ == "__main__":
    import cProfile, pstats
    profiler = cProfile.Profile()
    profiler.enable()
    workload()
    profiler.disable()
    stats = pstats.Stats(profiler)
    stats.sort_stats("cumulative")       # 按累计耗时排序
    stats.print_stats(10)                # 打印前 10 个热点
```

**运行并观察**：

```powershell
# ① cProfile：函数级耗时
python 13_profile_demo.py

# ② 导出数据给 snakeviz 可视化
python -m cProfile -o profile.out 13_profile_demo.py
snakeviz profile.out                     # 浏览器里看火焰图

# ③ py-spy：不用改代码，直接 attach 采样（生产安全）
py-spy top -- python 13_profile_demo.py

# ④ line_profiler：逐行耗时（需在函数上加 @profile 装饰器）
kernprof -l -v 13_profile_demo.py
```

**你会看到**：`slow_python` 占了绝大多数时间，`fast_builtin` 几乎可忽略——**热点一目了然**。

## 1. 一句话直觉

> **剖析器（profiler）= 性能的"X 光机"**：它照出你的程序"时间都花在哪一行、哪个函数"，让你不用瞎猜。

类比：程序慢就像"水管流水慢"，你不能凭感觉拆水管，要先装**流量计**（profiler）测出"哪一段管子最堵"，再精准疏通那一段。盲目优化非热点代码，是性能优化最常见的浪费。

## 2. 核心原理

### 2.1 四件工具的分工

| 工具 | 粒度 | 原理 | 何时用 |
|------|------|------|--------|
| **cProfile** | 函数级 | 插桩（instrumentation）：记录每个函数调用次数+耗时 | 找"哪个函数是热点" |
| **line_profiler** | 行级 | 插桩到每一行 | 找到热点函数后，定位"函数内哪一行慢" |
| **py-spy** | 采样 | 定时采样调用栈（不改代码，低开销） | 生产环境、正在跑的程序 |
| **snakeviz** | 可视化 | 把 cProfile 数据画成火焰图 | 直观浏览调用关系 |
| **timeit** | 微基准 | 重复执行计时 | 测"一行/一个表达式"的快慢 |

**标准流程**：

```
1. cProfile  → 找出热点函数（哪个函数耗时最多）
2. line_profiler → 定位热点函数里的热点行
3. 针对性优化那一行
4. 再 cProfile 验证 → 是否真的变快
```

### 2.2 cProfile：读懂统计输出

```python
stats.sort_stats("cumulative").print_stats(10)
```

关键列：

| 列 | 含义 |
|----|------|
| `ncalls` | 调用次数 |
| `tottime` | **自身耗时**（不含调用子函数）——找"这函数自己慢" |
| `cumtime` | **累计耗时**（含子函数）——找"这条调用链慢" |
| `percall` | 每次调用耗时 |

**经验**：先看 `cumtime` 找"大头函数"，再看 `tottime` 判断"是它自己慢，还是它调的函数慢"。

### 2.3 py-spy：不改代码就能剖析（生产利器）

```powershell
py-spy top -- python your_script.py    # 实时 top，看哪个函数在烧 CPU
py-spy record -o flame.svg -- python your_script.py   # 生成火焰图
py-spy dump --pid 12345                # attach 到正在运行的进程，打印当前栈
```

**为什么重要**：`cProfile`/`line_profiler` 要改代码（或包装启动），而且插桩有开销、可能干扰结果；`py-spy` 是**采样式**、**不用改代码**、**能 attach 线上进程**，是"程序已经在生产环境跑、突然变慢"时的救命工具。

### 2.4 GPU 侧剖析：torch.profiler

你的引擎大量时间在 GPU 上，Python 剖析器**看不到 kernel 耗时**。要用 `torch.profiler`：

```python
from torch.profiler import profile, ProfilerActivity

with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA]) as prof:
    model(x)                          # 你的推理

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=10))
# 打印每个算子（matmul、softmax、kernel）的 GPU 耗时
```

**关键概念**：GPU 是**异步**的，`time.time()` 测不准（它只测了"发起调用"的时间，没等 GPU 算完）。要测 GPU 耗时，要么 `torch.cuda.synchronize()` 卡住等结果，要么用 `torch.profiler` 看真实的 kernel 时间。

> 你第 03 篇自制的 `@cuda_time` 装饰器（`synchronize` + 计时）测的是"端到端墙钟时间"；`torch.profiler` 能进一步拆到"每个 kernel 各自多久"。两者配合，你就能回答"我的 attention 慢，是因为 Python 调度慢，还是某个 kernel 慢"。

### 2.5 90/10 原则与 Amdahl 定律

- **90/10**：程序 90% 时间通常花在 10% 的代码上。找到那 10% 才值得优化。
- **Amdahl 定律**：优化能带来的加速上限，受"不可优化部分"比例限制。`加速比 = 1 / (1 - 可优化比例 + 可优化比例/优化倍数)`。

> 直觉：如果某函数只占 1% 耗时，把它优化 100 倍，总程序也就快不到 1%。**先优化大头**。

## 3. 深入细节：micro-benchmark 的坑

`timeit` 测微小代码时，有几个坑要避开：

```python
import timeit

# ✅ 用 timeit 而非手写循环（它自动重复多次、取最优，排除抖动）
print(timeit.timeit("sum(range(1000))", number=10000))

# ❌ 手写计时易受 CPU 调度、缓存冷热影响，单次不可靠
```

**经验**：微基准用 `timeit`，宏观热点用 `cProfile`，GPU 用 `torch.profiler`，生产现场用 `py-spy`。工具选对，事半功倍。

## 5. 自测题

**Q1（概念）**：`tottime` 和 `cumtime` 的区别是什么？一个函数 `tottime` 很大但 `cumtime` 很小说明什么？

**Q2（应用）**：你发现推理总耗时 100ms，其中 `forward` 占 95ms。用 `line_profiler` 逐行看 `forward`，发现 `x = x.float()` 这一行占 90ms。这提示了什么优化方向？

**Q3（思考）**：为什么 `time.time()` 测 GPU 算子的耗时会"严重低估"？`torch.cuda.synchronize()` 在其中起什么作用？

<details>
<summary>点击展开答案</summary>

**A1**：`tottime` 是函数**自身代码**的耗时（不含它调用的子函数）；`cumtime` 是**包含子函数**的累计耗时。`tottime` 很大、`cumtime` 很小（或接近）说明：这个函数自己很慢、且几乎不调用别的慢函数——瓶颈就在这个函数体内部。

**A2**：`x.float()` 单行占 90ms，说明这行在**频繁做 dtype 转换**（可能每次 forward 都把整块张量转 float32，产生大量拷贝）。优化方向：① 尽量保持张量在同一个 dtype，避免反复转换；② 用 `half`/`bfloat16` 存储、只在必要时升精度；③ 避免在循环内重复转换——把转换提到循环外。

**A3**：GPU 是**异步执行**的——`torch.matmul` 只是"把命令提交到 GPU 队列"就立刻返回，Python 代码继续往下跑，此时 GPU 可能还没算完。`time.time()` 只测了"提交命令"的 CPU 时间，没等 GPU 算完，所以严重低估。`torch.cuda.synchronize()` 会**阻塞 CPU 直到 GPU 队列执行完**，之后 `time.time()` 才测到真实的端到端耗时（提交 + 排队 + 计算）。
</details>
