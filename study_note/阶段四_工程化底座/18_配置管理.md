# 18 · 配置管理：pydantic 把配置变成"有校验的强类型"

> **一句话定位**：配置管理从"硬编码 → dict → dataclass → pydantic"逐级演进。pydantic 让配置**有类型、有校验、能读环境变量、启动即失败**，是消灭"魔法数字 + 深夜配置 bug"的工业答案。
> **前置依赖**：08 类型系统
> **预计时长**：1 天
> **对应你的项目**：`model.py` 里的 `config` dict、`std=0.02`、`temperature=0.8` 等魔法数字，本篇一次性收编成强类型配置。

## 0. 先跑起来

先装 pydantic：

```powershell
uv add pydantic pydantic-settings     # 或 pip install pydantic pydantic-settings
```

```python
# 18_config_demo.py
from pydantic import BaseModel, Field, field_validator

# ── 1. 基础：类型 + 校验 + 默认值 ──
class ModelConfig(BaseModel):
    vocab_size: int = 50257
    n_embd: int = 768
    n_head: int = 12
    n_layer: int = Field(default=12, gt=0)          # gt=0：必须大于 0
    dropout: float = Field(default=0.1, ge=0, le=1) # 0~1 之间
    max_seq_len: int = 1000

    @field_validator("n_embd")
    @classmethod
    def check_divisible(cls, v: int, info) -> int:
        # n_embd 必须能被 n_head 整除（你原来用 assert 干的事，现在启动即校验）
        n_head = info.data.get("n_head", 1)
        if v % n_head != 0:
            raise ValueError(f"n_embd({v}) 必须能被 n_head({n_head}) 整除")
        return v

# 正常：自动补默认值
cfg = ModelConfig(n_embd=256, n_head=4)
print(cfg)                     # ModelConfig(vocab_size=50257, n_embd=256, ...)

# 校验失败：启动即报错，而不是运行到一半崩
try:
    ModelConfig(n_embd=256, n_head=3)     # 256 % 3 != 0
except ValueError as e:
    print("校验拦截:", e)

# ── 2. 从字典/JSON 构造 ──
raw = {"vocab_size": 100, "n_embd": 128, "n_head": 8, "n_layer": 2}
cfg2 = ModelConfig.model_validate(raw)    # 严格校验；也可 **raw 展开
print(cfg2.n_embd)

# ── 3. pydantic-settings：读环境变量 + .env ──
from pydantic_settings import BaseSettings, SettingsConfigDict

class EngineSettings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="ENGINE_", env_file=".env")

    backend: str = "torch"            # 对应环境变量 ENGINE_BACKEND
    device: str = "cpu"               # ENGINE_DEVICE
    max_batch_size: int = 8           # ENGINE_MAX_BATCH_SIZE
    weights_path: str | None = None   # ENGINE_WEIGHTS_PATH

# 假设 .env 文件里写了 ENGINE_BACKEND=triton，这里会自动读入
s = EngineSettings()
print(s.backend, s.device)
```

运行：`python 18_config_demo.py`。

## 1. 一句话直觉

> **pydantic = "给配置上保险"：你声明"这个字段是 int、必须在 0~1、必须能被整除"，pydantic 在**启动那一刻**就全查一遍——错配置**当场爆炸**，而不是半夜线上才炸。**

类比：配置就像**工程图纸的参数表**。手写 dict 是"随手记在便签上"（错了没人管）；dataclass 是"打印成表格"（有结构但没人验算）；pydantic 是"每项都过质检、盖章"（类型 + 范围 + 依赖关系全验算，不合格直接打回）。

## 2. 核心原理

### 2.1 配置管理的四级演进

| 阶段 | 形式 | 问题 |
|------|------|------|
| ① 硬编码 | `std = 0.02` 散落各处 | 魔法数字，改一处漏三处 |
| ② dict | `config = {"n_embd": 256}` | 无类型、无校验、拼错键静默 |
| ③ dataclass | `@dataclass class Config` | 有类型，但**校验要手写 `__post_init__`** |
| ④ **pydantic** | `class Config(BaseModel)` | 类型 + 校验 + 序列化 + 环境变量，一站式 |

你 `model.py` 现在处于 ②/③ 之间（有 `@dataclass Config`，但校验靠裸 `assert`）。目标：升到 ④。

### 2.2 pydantic v2 的核心 API

```python
from pydantic import BaseModel, Field, field_validator

class Config(BaseModel):
    n_layer: int = Field(default=12, gt=0)       # 约束：> 0
    dropout: float = Field(default=0.1, ge=0, le=1)  # 0~1
    kind: Literal["GPT", "Llama"] = "GPT"        # 有限取值

    @field_validator("n_embd")
    @classmethod
    def check(cls, v, info): ...                 # 字段级校验

    @model_validator(mode="after")               # 跨字段校验（用完整对象）
    def check_all(self): ...
```

**常见约束（`Field`）**：

| 参数 | 含义 |
|------|------|
| `gt` / `ge` | 大于 / 大于等于 |
| `lt` / `le` | 小于 / 小于等于 |
| `min_length` / `max_length` | 长度范围 |
| `pattern` | 正则匹配（字符串） |
| `default_factory` | 默认值的工厂 |

### 2.3 校验的两类：字段级 vs 跨字段

```python
# 字段级：只校验一个字段
@field_validator("n_embd")
def check_embd(cls, v): ...

# 跨字段：需要多个字段一起判断（如 n_embd 能被 n_head 整除）
@model_validator(mode="after")
def check_divisible(self):
    if self.n_embd % self.n_head != 0:
        raise ValueError("n_embd 必须能被 n_head 整除")
    return self
```

> 你原来 `assert n_embd % n_head == 0` 是**跨字段校验**，应放 `@model_validator`。这样配置一创建就校验，且**错误信息清晰、带上下文**。

### 2.4 pydantic-settings：环境变量 + .env + 优先级

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="ENGINE_", env_file=".env")
    backend: str = "torch"
```

**配置来源优先级**（高 → 低）：
1. 代码里显式传入的初始化参数
2. 环境变量（`ENGINE_BACKEND`）
3. `.env` 文件
4. 字段默认值

**为什么重要**：生产环境通过**环境变量**注入配置（如 `ENGINE_DEVICE=cuda`），**不碰代码**；本地开发用 `.env`；默认值兜底。这是 12-factor app 的核心理念——**配置和代码分离**。

### 2.5 消灭魔法数字

你代码里的魔法数字，收编进配置：

```python
# 现在（散落）：
std = 0.02                 # model.py
temperature = 0.8          # model.py generate
top_k = 200                # model.py generate

# 收编后：
class SamplingConfig(BaseModel):
    temperature: float = Field(default=0.8, gt=0)
    top_k: int = Field(default=200, gt=0)

class InitConfig(BaseModel):
    std: float = 0.02
```

**好处**：① 所有可调参数**集中可见**；② 有默认值和校验；③ 改参数只改一处；④ 能通过环境变量/配置文件覆盖（不用改代码）。

## 3. 深入细节：pydantic v2 的坑

### 坑 1：v1 和 v2 语法不同

```python
# v1（旧）：class Config: 内嵌类
class M(BaseModel):
    class Config:
        env_prefix = "X_"

# v2（新）：model_config = ConfigDict(...)
class M(BaseModel):
    model_config = ConfigDict(env_prefix="X_")
```

**2025 年务必用 v2 语法**（`model_config`）。网上大量旧教程是 v1 写法，会误导。

### 坑 2：`model_validate` vs `**dict` 展开

```python
cfg = Config.model_validate(raw)   # 推荐：严格校验，报错带字段路径
cfg = Config(**raw)                # 也可，但宽松些
```

### 坑 3：校验失败要"快速失败"

pydantic 的价值在于**启动即失败**。所以配置校验要**在程序开头就创建配置对象**，而不是"用到哪个字段才创建"。你 `model.py` 里 `Config(**ckpt['model_args'])` 在加载 checkpoint 时创建——是对的时机，但要把校验（如整除）也放进 pydantic，让它在那时就拦下坏配置。

## 5. 自测题

**Q1（概念）**：`@field_validator` 和 `@model_validator` 的区别是什么？"n_embd 能被 n_head 整除"该用哪个？

**Q2（应用）**：写一个 `SamplingConfig`，要求：`temperature` 必须 > 0（默认 0.8），`top_k` 必须是正整数（默认 200），且当 `temperature == 0` 时（贪心采样）`top_k` 必须被忽略（即允许任意值）。

**Q3（思考）**：为什么"配置和代码分离"（12-factor）对生产部署重要？环境变量注入相比"改代码里的常量"有什么本质优势？

<details>
<summary>点击展开答案</summary>

**A1**：`@field_validator` 校验**单个字段**（拿到的只是该字段的值 + `info`）；`@model_validator(mode="after")` 校验**整个对象**（能访问所有字段，做跨字段判断）。"n_embd 能被 n_head 整除"需要同时看两个字段，属于**跨字段**校验，用 `@model_validator(mode="after")`。

**A2**（示例）：
```python
class SamplingConfig(BaseModel):
    temperature: float = Field(default=0.8, ge=0)   # 允许 0（贪心）
    top_k: int = Field(default=200, gt=0)

    @model_validator(mode="after")
    def check_greedy(self):
        if self.temperature == 0 and self.top_k != 0:
            # 贪心时 top_k 无意义，可归一为 0 或直接允许
            return self
        return self
```
（更严谨：贪心时把 `top_k` 置 0 或在校验里 `if temperature==0: 跳过 top_k 检查`。核心是"温度 0 → 贪心，top_k 失效"这条业务规则的集中表达。）

**A3**：① **不改代码就能适配环境**——同一份代码，开发用 `device=cpu`、生产用 `ENGINE_DEVICE=cuda`，靠环境变量切换，不必为每个环境改代码/重建镜像；② **安全**——密钥、数据库地址等敏感配置不进代码库（代码会进 git、会分享，环境变量是运行时注入）；③ **可移植/可伸缩**——Docker/K8s 天然支持环境变量注入，配置随部署环境流动；④ **可审计**——配置变更有部署系统的记录，而非藏在某次代码提交里。这就是 12-factor 的"配置与代码分离"。
</details>
