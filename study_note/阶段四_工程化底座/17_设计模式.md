# 17 · 设计模式：SOLID + 依赖注入 + 策略/工厂/适配器

> **一句话定位**：设计模式不是背套路，而是"让代码容易改、容易测、容易扩展"的结构化经验。Python 里很多模式被简化了——你项目里的 `Backend` 抽象已经暗合"策略模式"，本篇让它显式化、可扩展化。
> **前置依赖**：04 OOP
> **预计时长**：1 天
> **对应你的项目**：`Backend`/`TorchBackend` 是策略模式雏形，`Config` 是数据容器，`TORCH_LIBRARY` 是注册表模式——本篇系统化这些"你已经在用但没意识到的模式"。

## 0. 先跑起来

```python
# 17_design_patterns_demo.py
from abc import ABC, abstractmethod

# ── 1. 策略模式：接口 + 多个可替换实现（你 Backend 就是这个！） ──
class Backend(ABC):
    @abstractmethod
    def rmsnorm(self, x, w, eps=1e-6): ...

class TorchBackend(Backend):
    def rmsnorm(self, x, w, eps=1e-6): return x  # 简化示意

class TritonBackend(Backend):
    def rmsnorm(self, x, w, eps=1e-6): return x

# ── 2. 工厂模式：按名字/枚举造对象 ──
def backend_factory(kind: str) -> Backend:
    match kind:
        case "torch":  return TorchBackend()
        case "triton": return TritonBackend()
        case _:        raise ValueError(f"未知后端: {kind}")

be = backend_factory("torch")   # 调用方不关心具体类，只关心接口

# ── 3. 注册表模式：装饰器 + 字典，实现"自动发现" ──
REGISTRY = {}
def register(name):
    def deco(cls):
        REGISTRY[name] = cls
        return cls
    return deco

@register("torch")
class T(Backend):
    def rmsnorm(self, x, w, eps=1e-6): return x

@register("triton")
class Tri(Backend):
    def rmsnorm(self, x, w, eps=1e-6): return x

print(REGISTRY)                       # {'torch': <class T>, 'triton': <class Tri>}
be = REGISTRY["triton"]()             # 按名字从注册表取类，再实例化

# ── 4. 依赖注入：把依赖从"内部 new"改成"外部传入" ──
class Model:
    def __init__(self, backend: Backend):   # 注入：不自己 new，由外部给
        self.backend = backend
    def forward(self, x):
        return self.backend.rmsnorm(x, None)

m = Model(TorchBackend())                   # 测试时注入假的，生产注入真的
```

运行：`python 17_design_patterns_demo.py`。

## 1. 一句话直觉

> **设计模式 = 应对"变化"的套路。策略模式应对"算法会换"（换后端），工厂模式应对"创建会变"（按配置造对象），依赖注入应对"依赖会换"（测试换假的），注册表模式应对"要自动发现新实现"（加算子不用改调度代码）。**

类比：策略模式像**可换插头的插座**——设备（模型）不关心电流（实现）来自哪个插头（后端），只要接口匹配，换插头就行。工厂像**点餐窗口**——你说"来份牛肉面"（名字），厨房（工厂）给你端出来，你不关心谁做的。依赖注入像**租客带自己的家具**——房子（类）不负责买家具（依赖），谁住谁带。

## 2. 核心原理

### 2.1 SOLID 五原则（用你的项目对照）

| 原则 | 一句话 | 你的项目对照 |
|------|--------|-------------|
| **S** 单一职责 | 一个类只干一件事 | `LlamaBlock` 只装一层、`Backend` 只管算子——✅ |
| **O** 开闭原则 | 对扩展开放、对修改关闭 | 加新后端不用改 `Model`，只加新类——✅ 靠 `Backend` 抽象实现 |
| **L** 里氏替换 | 子类能安全替换父类 | 任何 `Backend` 子类都能替换进 `Model`——✅ |
| **I** 接口隔离 | 接口要小、专用 | `Backend` 只有 3 个算子方法，没有无关方法——✅ |
| **D** 依赖倒置 | 依赖抽象，不依赖具体 | `Model` 依赖 `Backend` 抽象，不依赖 `TorchBackend`——✅ |

**惊喜**：你项目里 `backend.py` 开头注释写的"上层只认接口、不认实现"，**就是 SOLID 里 O + D 的完整实践**。你已经无意识地做对了大部分——本篇是让你**意识到**，从而能主动、系统地应用。

### 2.2 策略模式（Strategy）：你的 `Backend` 就是这个

```python
class Model:
    def __init__(self, backend: Backend):   # 持有"策略"接口
        self.backend = backend
    def forward(self, x):
        return self.backend.rmsnorm(x, ...)  # 委托给策略，不自己实现

model_torch = Model(TorchBackend())    # 换策略 = 换一行构造参数
model_triton = Model(TritonBackend())
```

**价值**：加新后端（如 `CudaBackend`）时，**零改动** `Model`——只新增一个类。这就是"开闭原则"。

### 2.3 工厂模式（Factory）：把"创建逻辑"集中起来

你 `model.py` 里散落的 `GPT(...)` / `LlamaModel(...)` 创建逻辑，用工厂集中：

```python
class ModelFactory:
    @staticmethod
    def create(kind: ModelKind, config: Config, backend: Backend) -> nn.Module:
        match kind:
            case ModelKind.GPT:   return GPT(config, backend)
            case ModelKind.LLAMA: return LlamaModel(config, backend)
```

**价值**：创建逻辑（含校验、默认值、日志）集中在一处，调用方只传"参数"不写"构造细节"。你 `model.py` 的 `if choose=="GPT": ... elif choose=="Llama":` 就适合提炼成工厂。

### 2.4 依赖注入（Dependency Injection）

**核心**：类**不自己创建**依赖，而是**通过构造参数接收**依赖。

```python
# ❌ 硬编码：Model 内部自己 new 后端，测试时无法换成假的
class Model:
    def __init__(self):
        self.backend = TorchBackend()   # 绑死了！

# ✅ 依赖注入：后端由外部传入
class Model:
    def __init__(self, backend: Backend):
        self.backend = backend
```

**最大好处：可测试性**。测试时注入一个**假后端**（mock），就不用真的跑 CUDA；生产注入真后端。你已经这么写了（`Model(config, backend)` 传入 `TorchBackend()`），继续保持。

### 2.5 适配器模式（Adapter）：统一不同接口

当你有两个不同库、接口不一致，想统一调用时，用适配器"翻译"：

```python
class TritonBackendAdapter(Backend):       # 把 triton 的实现"适配"成 Backend 接口
    def __init__(self, triton_impl):
        self._impl = triton_impl
    def rmsnorm(self, x, w, eps=1e-6):
        return self._impl.triton_rmsnorm(x, w, eps)   # 翻译：不同方法名 → 统一接口
```

**价值**：让"外部库/第三方实现"能接入你的统一抽象，上层无感知。你以后接 vLLM 的 kernel、或别人的 Triton 实现，用适配器包一层即可。

### 2.6 Python 里"模式被简化"的真相

很多 GoF 设计模式在 Python 里因为**一等函数、鸭子类型、装饰器**而大幅简化：

- **策略模式**：甚至不需要接口类——直接传函数也行（`model(backend=rmsnorm_func)`）。
- **命令模式**：一等函数 + `functools.partial` 就够，不必建 Command 类。
- **观察者模式**：直接回调函数列表，不必建 Observer 接口。

> **原则：Python 里"简单即美"，能用函数解决的别硬套类层次**。你 `model.py` 的 `encode = lambda s: ...`、`temp_topk` 内嵌函数，都是"用函数而非类"的 Python 味。别为了"显得有设计模式"而过度设计。

## 3. 深入细节：别过度设计

**设计模式的正确使用时机是"第二次出现变化时"**：

```
第一次写某个功能 → 直接写，别套模式（YAGNI：You Aren't Gonna Need It）
第二次出现同类变化 → 提炼共同点，引入模式（DRY：Don't Repeat Yourself）
第三次 → 模式已经证明价值，保持
```

**反例**：一个项目只有一种后端，却搞出一套 `BackendFactory` + `BackendRegistry` + `BackendProvider`——纯属过度设计，难读难改。

**你的判断**：你的引擎**明确会多后端**（Torch/Triton/CUDA），所以 `Backend` 抽象**不算过度设计**，是**恰到好处**。继续保持，但别再加无谓的抽象层。

## 5. 自测题

**Q1（概念）**：SOLID 的 O（开闭原则）和 D（依赖倒置）分别是什么意思？你的 `Backend` 抽象如何同时体现了这两条？

**Q2（应用）**：把下面的硬编码改造成依赖注入 + 策略模式：

```python
class InferenceService:
    def __init__(self):
        self.engine = TorchEngine()   # 绑死了具体实现
    def run(self, req):
        return self.engine.generate(req)
```

**Q3（思考）**：为什么"依赖注入"能显著提升可测试性？它和"mock"（第 16 篇）是什么关系？

<details>
<summary>点击展开答案</summary>

**A1**：**开闭原则（O）**：对扩展开放、对修改关闭——加新功能（新后端）应该通过**新增类**实现，而不是改现有类的代码。**依赖倒置（D）**：高层模块（Model）应依赖**抽象**（Backend 接口），不依赖具体实现（TorchBackend）。你的 `Backend` 抽象：加新后端 = 新增一个 `XxxBackend` 类（O，不改 Model）；Model 依赖 `Backend` 接口而非具体类（D）。

**A2**：
```python
class InferenceService:
    def __init__(self, engine: Engine):    # 注入抽象
        self.engine = engine
    def run(self, req):
        return self.engine.generate(req)

service = InferenceService(TorchEngine())      # 生产注入真引擎
service = InferenceService(FakeEngine())       # 测试注入假引擎
```

**A3**：依赖注入让"依赖"成为**可替换的构造参数**，测试时**从外部注入 mock 对象**（第 16 篇的 mock/monkeypatch），就能在**不触达真实依赖**（不跑 CUDA、不连网络、不读真实 checkpoint）的情况下测试被测类的逻辑。若依赖是内部硬编码 `new` 出来的，测试就无法拦截替换，只能被迫依赖真实环境。所以 DI 是 mock 得以生效的**结构前提**：可注入，才可 mock。
