# 15 · 项目结构与打包：从"一堆脚本"到"可安装的包"

> **一句话定位**：`pyproject.toml` + `src` 布局 + `uv` 是把你的代码变成"别人能 `pip install`、能复用、能进 CI"的工业包。这是"工程交付能力"的第一块拼图。
> **前置依赖**：10 代码风格
> **预计时长**：1 天
> **对应你的项目**：你的 `推理引擎` 现在没有 `pyproject.toml`、用非 ASCII 包名、靠 `__main__` 跑——本篇把它变成规范的包。

---

## 0. 先跑起来

```powershell
# 用 uv 初始化一个标准项目（体验现代打包流程）
uv init my_pkg                # 生成 pyproject.toml + src 布局
cd my_pkg
uv add numpy                  # 添加依赖，自动写进 pyproject.toml 并生成 lock
uv sync                       # 按 lock 文件安装依赖
uv run python -c "import my_pkg"   # 在项目环境里运行
```

看一下 `uv init` 生成的 `pyproject.toml` 长什么样：

```toml
[project]
name = "my_pkg"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = []            # uv add 会往这里加

[build-system]
requires = ["hatchling"]     # 构建后端
build-backend = "hatchling.build"

[tool.uv]
package = true               # 标记这是个可安装的包
```

## 1. 一句话直觉

> **打包 = 给你的代码办"身份证 + 快递箱"。`pyproject.toml` 是身份证（名字、版本、依赖、入口），`src` 布局是标准快递箱（清晰的目录结构），`uv` 是物流系统（装依赖、锁版本、发运）。**

类比：没打包的代码像"堆在桌上一堆散纸"，只有你自己知道怎么用；打包后像"装订成书、有目录、能上架的书"，任何人（包括 CI、同事、未来的你）都能按标准流程拿到手。

---

## 2. 核心原理

### 2.1 `pyproject.toml` 的三大板块

```toml
[project]                    # ① 元数据：给人和工具看
name = "inference-engine"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["torch>=2.0"]

[project.optional-dependencies]   # ② 可选依赖分组
dev = ["pytest", "ruff", "mypy"]
cuda = ["triton>=2.0"]

[project.scripts]                # ③ 命令行入口
infer = "inference_engine.cli:main"   # 装完后终端敲 infer 就调 main()

[build-system]                   # ④ 构建后端
requires = ["hatchling"]
build-backend = "hatchling.build"
```

| 板块 | 作用 |
|------|------|
| `[project]` | 名字、版本、依赖、Python 版本要求 |
| `[project.optional-dependencies]` | 按场景分组的依赖（`pip install -e .[dev]`） |
| `[project.scripts]` | 命令行入口（`console_scripts`） |
| `[build-system]` | 用哪个后端构建（hatchling/setuptools/poetry-core） |

> 2025 年主流后端：**hatchling**（快、现代、uv 默认）或 **setuptools**（老牌）。用 uv 默认的 hatchling 即可。

### 2.2 `src` 布局 vs 平铺布局

```
# 平铺布局（老式，问题多）：
my_pkg/
├── my_pkg/          # 包和 pyproject 平级
├── tests/
└── pyproject.toml

# src 布局（推荐）：
my_pkg/
├── src/
│   └── my_pkg/      # 包在 src 下
├── tests/
└── pyproject.toml
```

**为什么推荐 `src` 布局**：
1. **强制"测试安装后的包"**：src 布局下，直接 `python` 找不到包，必须先 `pip install -e .`。这保证你测试的**永远是"装出来"的包**，而不是"当前目录碰巧能 import"的包，避免"本地能跑、装给别人就坏"。
2. 避免"导入当前目录的未安装版本"导致的隐性 bug。

### 2.3 `uv` 三件套

| 命令 | 作用 |
|------|------|
| `uv add <pkg>` | 加依赖 + 更新 lock |
| `uv sync` | 按 lock 精确安装（可复现） |
| `uv run <cmd>` | 在项目虚拟环境里运行命令 |
| `uv pip install -e .` | 可编辑安装（开发模式） |
| `uv lock` | 生成/更新 lock 文件 |

**editable install（可编辑安装）**：`pip install -e .` 后，你**改源码立即生效**，不用每次重装——开发时的标准姿势。你 `model.py` 里 `from 推理引擎.engine.backend import ...` 这种导入，只有在"装成包"后才能被任何地方正常引用。

### 2.4 修掉你的非 ASCII 包名

你现在的导入路径是 `from 推理引擎.engine.backend import ...`。**中文包名能跑，但极不规范**：
- 某些工具/CI/跨平台环境对非 ASCII 路径支持差。
- 别人（或面试官）看到 `import 推理引擎` 会觉得"不专业"。

**改法**：把 `推理引擎` 重命名成 ASCII 包名，如 `inference_engine`（或 `llm_engine`），目录结构：

```
PythonProject1/
├── pyproject.toml
├── src/
│   └── inference_engine/
│       ├── __init__.py
│       ├── engine/
│       │   ├── __init__.py
│       │   ├── backend.py
│       │   ├── model.py
│       │   ├── rope.py
│       │   └── PagedAttention.py
│       └── cli.py           # 命令行入口
├── tests/
│   ├── test_backend.py
│   └── ...
└── cuda_ext/                # 你的 CUDA 扩展（单独构建，见第 20 篇）
```

然后所有 `from 推理引擎.engine.X import Y` 改成 `from inference_engine.engine.X import Y`。

> ⚠️ **重命名是大工程，建议和"重构"一起做**（第 24 篇综合实战统一处理）。本篇先学会"怎么打包"，第 24 篇一次性落地。

## 3. 深入细节：入口点与 CLI

`[project.scripts]` 让你的包提供一个**命令行命令**：

```python
# src/inference_engine/cli.py
def main():
    import argparse
    p = argparse.ArgumentParser(description="推理引擎 CLI")
    p.add_argument("--model", choices=["GPT", "Llama"], required=True)
    p.add_argument("--prompt", default="")
    args = p.parse_args()
    # ... 加载模型、生成 ...

if __name__ == "__main__":
    main()
```

```toml
[project.scripts]
infer = "inference_engine.cli:main"
```

装完后：`infer --model GPT --prompt "你好"` 直接可用。这就是"把 `if __name__ == "__main__"` 里的散代码，升级成标准 CLI"。

**工业惯例**：用 `argparse`（标准库）或 `typer`（更现代，基于类型标注自动生成 CLI）代替手写 `input()`/`choose=input(...)`。你 `model.py` 的 `choose=input("选择模型 (GPT / Llama): ")` 交互式输入，无法被脚本化/CI 调用，改成 argparse 参数是工业化的必然。

## 5. 自测题

**Q1（概念）**：`src` 布局相比平铺布局的核心优势是什么？为什么它"强制你测试安装后的包"？

**Q2（应用）**：写出一个 `[project.scripts]` 入口，让安装后终端输入 `engine-bench --warmup 3` 能调用 `inference_engine.benchmark.main(warmup=3)`。

**Q3（思考）**：`uv sync` 和 `pip install -r requirements.txt` 的本质区别是什么？为什么 lock 文件对"可复现的工业交付"重要？

<details>
<summary>点击展开答案</summary>

**A1**：src 布局把包放进 `src/`，当前目录不在 import 路径上，所以**必须先 `pip install -e .` 才能 import**。这保证你测试/运行的**永远是"安装出来的包"**，而不是"碰巧在 cwd 里能被 import 的源码"——避免"本地能跑、装给用户/CI 就坏"（比如漏了 `__init__.py`、漏了打包配置、路径依赖）这类问题。

**A2**：
```toml
[project.scripts]
engine-bench = "inference_engine.benchmark:main"
```
调用约定：`engine-bench --warmup 3` 会把 `--warmup 3` 解析后传给 `main`。对应代码里 `main()` 用 argparse 接收 `--warmup` 参数（或 `main(warmup=3)` 由入口自动传，取决于入口是"直接指定函数"还是"指定到含 argparse 的 main"——标准做法是入口指向一个无参 `main()`，参数用 argparse 解析）。

**A3**：`requirements.txt` 只写**顶层依赖**且常不锁版本（或写 `>=` 范围），每次安装可能解析出**不同的子依赖版本**，导致"我的机器能跑、你的不能"；`uv sync` 依据 **lock 文件**（记录了**所有**依赖的**精确版本 + 哈希**）安装，保证任何机器、任何时候装出来**完全一致**，这是"可复现交付"的根基。这也是 CI、Docker 镜像、团队协作能稳定复现的前提。
</details>
